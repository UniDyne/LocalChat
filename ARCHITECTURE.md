# Architecture — LocalChat

## Stack

| Layer | Technology |
|-------|------------|
| Desktop framework | Wails v2 (Go backend + native WebView) |
| Backend | Go 1.26, talking to a local Ollama instance via `github.com/ollama/ollama/api` |
| Persistence | DuckDB (`sessions.db`), embedded — sessions, messages, artifacts |
| Frontend | Vanilla HTML/CSS/JS, no framework; Vite for dev server + build |
| Packaging | `wails.json` config; `wails build` embeds the built frontend into a native binary via `//go:embed` |

There is no separate HTTP API — the frontend calls Go methods directly
through Wails' generated JS bindings (`frontend/wailsjs/go/main/App.js`),
and the backend pushes live updates back with Wails events
(`chat:message`, `chat:status`, `session:renamed`, `artifact:created`).

> **Note on `frontend/wailsjs/`:** these files are normally regenerated by
> the `wails` CLI (`wails generate module` / as part of `wails dev`/`wails
> build`) from `app.go`'s method signatures. In this environment they have
> at times been hand-edited to match a changed `App` method signature (e.g.
> adding a parameter to `SendChat`) when the CLI wasn't available. If you
> add or change the signature of an exported `App` method, either run the
> Wails CLI to regenerate these bindings or update
> `frontend/wailsjs/go/main/App.js` and `App.d.ts` by hand to match.

## Data model (DuckDB)

Three tables, defined in `store.Open`:

- **`sessions`** — `id`, `title`, `created_at`. Titles start as "New Chat"
  and are rewritten from the user's first message as soon as it's sent (see
  `isFirstMessage` handling in `SendChat`), independent of whether the model
  ever replies.
- **`messages`** — one row per message in a turn: `role` (`user`, `cot`,
  `tool`, or `assistant`), `content`, `model`, `mode`, `pinned`, and
  `tool_name`/`tool_args`/`tool_result` (populated for `tool` rows, and for
  a `user` row that was auto-dispatched from a queued task list rather than
  typed — see "Turn lifecycle" below). `(session_id, seq)` is the primary
  key; `seq` is assigned under a lock spanning both the read of the current
  max and the insert, so it can't collide under concurrent writes to the
  same session.
- **`artifacts`** — persisted content (`title`, `content`, `content_type`)
  created via the `create_artifact` tool, independent of the message log.

## Turn lifecycle (`SendChat` in `app.go`)

1. The user message is persisted immediately (`role: "user"`), before any
   model call — so a turn that errors out partway through still leaves a
   full record of what happened.
2. If a custom (file-based) cot mode is active, a **hidden evaluation
   pass** runs: the mode's `conf/cot/<name>.md` file, wrapped in framing
   that makes its role explicit (`cotEvalWrapper`), is sent as a system
   message ahead of the conversation history, with `Options.num_predict`
   capped per the mode's `max_tokens` frontmatter (default `1024`). The
   result is persisted as an unpinned `role: "cot"` row and folded into the
   *final user turn itself* (`cotAnswerWrapper`) — not the system message —
   so it's the last thing the model reads before generating, rather than
   competing with the whole system prompt + history for attention. The
   plain original prompt is what actually gets persisted/reused as history,
   so future turns never see the model's own past reasoning notes replayed
   back as if the user had written them.
3. **Tool-calling loop** (`chatWithTools`): sends the request with the tool
   registry attached, executes any requested tool calls, feeds results back,
   and repeats (capped at `maxToolIterations`) until the model replies with
   no more tool calls. Each tool call is persisted immediately as an
   unpinned `role: "tool"` row and emitted live via the `chat:message`
   event, so multi-step turns show progress as they happen rather than all
   at once at the end. `queue_tasks` is special-cased to end the turn the
   moment it's dispatched — the frontend, not the model, drives the
   follow-up tasks one at a time.
4. The final assistant reply is persisted as `role: "assistant"` and
   returned to the frontend alongside every other message produced this
   turn.

Queued follow-up tasks are re-sent through this same `SendChat` path with a
`queuedByTool` parameter set (currently always `"queue_tasks"`), which forces
the effective cot mode to `none` for that call regardless of the UI's
current selection, and is persisted on the row's `tool_name` — this is what
lets a reloaded session still tell a queued step apart from something the
user actually typed (see `UI.md`'s note on `.msg-task` styling).

## Separation of Concerns (frontend)

### `frontend/src/api.js` — Backend Abstraction Layer
Every call into the Go backend goes through this file's exported functions,
which wrap the generated Wails bindings. The rest of the frontend never
imports from `wailsjs/` directly.

### `frontend/src/app.js` — Chat Controller
Owns the in-memory `timeline`, the send/receive loop (`sendAndRender`),
rendering (`addMessage`/`renderIncomingMessage`), the status bar (including
its live elapsed-time counter), the queued-task auto-continuation loop, and
the live `chat:message`/`chat:status` event handlers. Timing is tracked
entirely client-side (`phaseStartedAt`, reset on turn start / each
`chat:status` event / each rendered message) — the backend sends no
duration data, so per-message timing badges only exist for the live session
and aren't persisted.

### `frontend/src/sessions.js` — Session List
Session CRUD/switching and the sidebar list. Listens for the `session:renamed`
live event so a session's title updates immediately when the backend
auto-titles it, instead of waiting for the whole turn to finish.

### `frontend/src/artifacts.js` — Artifacts Sidebar
Lists and displays artifacts created via `create_artifact`, refreshed on the
`artifact:created` event.

### `frontend/src/content.js` — Rendering
Markdown (`marked` + `math-marked` for LaTeX) and syntax highlighting
(`highlight.js`, a curated language subset to keep bundle size down).

### `frontend/index.html` — Presentation Layer
Single static HTML shell — all structure in one place, styled via CSS custom
properties in `app.css`. Vite processes the imported JS modules but doesn't
template the HTML body itself.

### `app.go` — Backend Orchestration
Loads `config.json`, holds the Ollama client/session store, and implements
every Wails-exported method: `SendChat` (turn orchestration, described
above), session management, message pin/unpin, and cot-mode listing/loading.

### `store/` and `skill/` — Persistence and Skill Discovery
`store` wraps all DuckDB access behind typed methods. `skill` discovers,
loads, and writes skill files under `conf/skills/` by parsing a small
hand-rolled frontmatter format (name/description) — deliberately not a full
YAML parser, since skill files only need flat single-line string fields.

## Design Decisions

- **Direct Go bindings via a thin JS abstraction** (`api.js`) — no HTTP
  layer between frontend and backend. Keeps the app simple while leaving a
  single seam if that ever needs to change.
- **Markdown-file-driven extensibility** — new cot modes and skills are
  just files under `conf/`, re-read on every use rather than cached, so
  hand-editing them takes effect without restarting the app. No code changes
  needed to add either.
- **Two-pass, recency-ordered chain-of-thought** instead of relying on a
  model's native thinking mode — see "Turn lifecycle" above and `README.md`
  for the reasoning behind folding the hidden notes into the final user turn
  rather than the system prompt.
- **Persist-as-you-go, not persist-at-the-end** — every message in a turn is
  written to the DB and emitted live the moment it's produced, so a turn
  that errors out (timeout, tool-iteration cap) still leaves a complete,
  inspectable record instead of losing everything back to the last
  successful turn.
- **Client-side-only timing** — generation duration is measured entirely in
  the frontend from event arrival times, not sent by the backend, since it's
  a live-session UX affordance, not something that needs to survive a
  reload.
